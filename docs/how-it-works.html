The short version

A buyer sends Nox a purchase order as a PDF, a photo, a spreadsheet or an email. The app has an AI read it and fill in a strict form (alloy, temper, size, quantity, certs). Then plain code checks that form against Nox's catalog and API rules, flags anything missing or risky, and builds the exact request Nox's quoting system accepts. A person reviews, fixes what's flagged, and sends it.

Why it exists

The problem

Nox sells cut-to-size metal (mostly aluminum plate and bar) and promises instant quotes. Their website has a clean quote form, and they have a public API, POST /api/v1/rfqs, that prices a request automatically through their internal quoting engine, Wayne.

But a lot of real orders don't arrive through that form. An aerospace buyer emails a two-page PDF purchase order. A tool-and-die shop sends a photo of a handwritten note. An engineer exports a spreadsheet with one row in millimetres. Today, a person at Nox reads each one and retypes it into the system.

That retyping is slow, and it's where mistakes happen: the wrong temper, a missed DFARS requirement, a quantity that changed in the third email of a thread. This app does the reading and the checking, and leaves a person to make the judgment calls.

What holds it together

Core principles

If you remember nothing else about the codebase, remember these five ideas. Almost every design decision follows from one of them.

1

The AI reads. Code decides.

Language models are excellent at reading messy documents: handwriting, odd layouts, "actually make that 15" buried in a reply. They're less reliable at following business rules exactly, every time. So the app splits the work. The AI's only job is to report what the document says. Whether that's acceptable to Nox is decided by plain code that behaves the same way on every run and can be tested.

Think of the AI as a sharp new hire who reads the fax and fills out the order form, and the rules as the supervisor's checklist that every form must pass before it goes to the shop floor.

The AI does

  • Find the line items, wherever they are on the page
  • Read handwriting and skip crossed-out lines
  • Notice a quantity that changed in a later revision
  • Suggest questions a buyer would want answered

The code does

  • Check alloy and temper against Nox's catalog
  • Enforce API limits (quantity 1 to 200, inches only)
  • Decide what blocks a line and what's just a warning
  • Build the request in Nox's exact format
2

Every value comes with a receipt

The AI doesn't just say "alloy is 7075". For every field it returns three things: the value, how confident it is, and the exact text it read the value from. In the app, hovering any cell shows that quote, so a reviewer can verify it in a second instead of hunting through the PDF.

// what the AI returns for one field (real output, Corvane PO line 20)
"quantity": {
  "value": 12,
  "confidence": "high",
  "source": "LINE 20 QTY CHANGED FROM 10 TO 12."
}

The line itself says "QTY WAS 10". The AI found the revision note elsewhere on the page and quoted it as its source for 12.

3

Never guess silently

When something is missing, ambiguous or risky, the app says so with a flag instead of quietly picking an answer. Each flag has a severity, a plain-English message, and usually a ready-made question for the buyer. One button turns all the open questions into an email.

SeverityWhat it meansReal example (Corvane PO)
ErrorThis line can't be quoted as-is. It's left out of the request until fixed.Line 10: "2219 plate isn't in Nox's catalog; not stocked, route to sales."
WarningProbably fine, but a person should confirm before sending.Line 50: "Temper not specified; Nox stocks 7050 plate only as T7451." Suggested question: "OK to quote 7050-T7451?"
NoteUseful context, nothing to fix.Line 20: "Revision A changes line 20 from 10 to 12 pieces; 12 pieces extracted."

Flags come from both sides. The rules raise the hard ones (not in catalog, quantity over 200, date too tight). The AI raises the judgment calls a person would notice, like quality clauses that are referenced but not attached.

4

Speak Nox's language exactly

The output isn't a summary. It's the exact request Nox's real API accepts, built from their published OpenAPI spec. That spec has strict rules, and the app follows all of them:

  • alloy is the bare code ("7075") and temper is a separate field ("T7351").
  • Both must appear in Nox's materials list for that form (plate or bar). Tube isn't quoted at all.
  • Dimensions are decimal inches. Quantity is 1 to 200 per line, and an RFQ has 1 to 100 lines.
  • Compliance is one of none, dfars or domestic. Certifications are a family (AMS, QQ, ASME, ASTM) plus a designation.
  • The API has no field for need-by date, PO number or cut tolerance, so those go into each line's free-text job_detail.
5

Safe by default

Creating an RFQ at Nox is a real action at a real company, so nothing is sent unless three things are all true: a Nox API key is configured, a person clicks Submit to Nox, and they confirm. Otherwise the app does a dry run: it shows the exact request it would send, as JSON and as a copyable curl command.

Every live request also carries an Idempotency-Key, a fingerprint of its contents. If someone double-clicks or a retry happens, Nox recognizes the same request and doesn't create a duplicate.

The same thinking covers data. Uploaded documents can be real customer POs, so they're never logged and never committed to git. Only the fictional sample documents are.

Worked example

One line, start to finish

Here's line 20 of the sample Corvane Launch Systems PO (a fictional launch-vehicle company) at each station. Everything below is real output from the app.

  1. 1. In the PDFsamples/09-launch-vehicle-po.pdf

    A row in the PO's line table, plus a revision note further down the page.

    20  MS-7075-T7351-1500  PLATE, AL 7075-T7351
                        1.500 X 12.00 X 24.00 IN
                        SPEC: AMS 4078
                        SAW CUT TOL +.060/-0
                        REV A: QTY WAS 10        12  EA  10/16/2026

NOTES  1. REVISION A (10/01/2026): LINE 20 QTY CHANGED FROM 10 TO 12.
  2. 2. Extractlib/extract-openai.ts

    The AI fills in the form. Each field gets a value, a confidence and a source quote.

    alloy       7075        high    "PLATE, AL 7075-T7351"
temper      T7351       high    "PLATE, AL 7075-T7351"
thickness   1.5         medium  "1.500 X 12.00 X 24.00 IN"
quantity    12          high    "LINE 20 QTY CHANGED FROM 10 TO 12."
certs       AMS 4078
tolerance   +.060/-0
  3. 3. Normalizelib/normalize.ts

    Six small cleanup steps run on every line: split a temper glued onto the alloy, fill gaps from spec callouts (AMS 4078 means 7075-T7351 plate), infer DFARS or domestic requirements from the text, convert millimetres, put the smallest plate dimension in thickness, and map a requested temper to the one Nox stocks (T6 on plate becomes T651, with a warning).

    This line was already clean, so nothing changed. The DFARS step left it alone because the PO limits DFARS to line 40.

  4. 4. Validatelib/validate.ts

    The rules check it: 7075-T7351 is in the plate catalog, all three plate dimensions are present, quantity 12 is between 1 and 200, need-by 10/16 isn't tight. No errors. The only flag on this line is the AI's note about the revision.

  5. 5. Build the requestlib/payload.ts

    The line becomes one entry in the body of POST /api/v1/rfqs. Things the API has no field for go into job_detail.

    {
  "ref": "20",
  "alloy": "7075",
  "temper": "T7351",
  "product_type": "Plate",  "shape": "Plate",
  "thickness": 1.5,  "width": 12,  "length": 24,
  "requested_quantity": 12,
  "certifications": [{ "family": "AMS", "designation": "AMS 4078" }],
  "job_detail": "PO CLS-PO-26-03318; Cust P/N MS-7075-T7351-1500;
                 Cut tol +.060/-0; Need by 2026-10-16; Mill certs (MTR) required; ..."
}

    Lines 10 (2219 aluminum) and 40 (Inconel 718) have errors, so they're held back. Lines 20, 30 and 50 go in the request.

  6. 6. Review and sendapp/page.tsx

    In the app, the reviewer sees the line in the table with no marks (high confidence, no problems), confirms the line 50 temper question, copies the questions as an email to the buyer, and clicks Create RFQ (dry run) or, with a key, Submit to Nox. Editing any cell reruns stations 4 and 5 instantly in the browser, so flags and the request update as you type.

Station 2, up close

How the AI part works

The app sends the document to a language model along with instructions (lib/prompt.ts) and a schema: a precise description of the form it must fill in. This uses a feature called structured output. The model can only reply with JSON that matches the schema, so the app never has to pick values out of a paragraph of prose.

The instructions carry metal-buyer knowledge: spec numbers and the alloys they imply, what "MTR" or "C of C" means, how to read "1/2 x 12 x 24", that a revised quantity beats the original, and to put a flag on anything it isn't sure of instead of guessing. They also include Nox's current materials list and today's date, so "need by thurs" resolves to a real date.

Three AI providers plug into the same slot. All of them get the same instructions and must fill in the same schema, so everything after station 2 doesn't know or care which one was used:

The cache: why the demo is instant

A live read of a two-page PO takes one to two and a half minutes. Reading the same file always gives the same answer, so the app saves the AI's output keyed by a fingerprint of the file (a SHA-256 hash: a short code that changes completely if even one byte of the file changes). The next time the same file comes in, station 2 is skipped and the answer comes back in milliseconds.

Only the AI's reading is cached. Stations 3 to 5 still run every time, so date checks use today's date and catalog changes apply. Cached results are labelled as cached and have a Re-run live button. The four featured samples ship with their cached readings, so the demo works without any AI connected. Your own uploads are cached on your machine only.

Proof

How we know it works

There are two kinds of checks, matching the AI/code split.

Unit tests (83 of them) cover the code side: unit conversions, spec lookups, every validation rule, the request builder, the cache, the ChatGPT sign-in flow and the AI response handling. They use fake AI responses, so they run in under a second with no keys and give the same result every time.

Samples with answer keys cover the AI side. There are nine messy documents (an email, a forwarded thread, a spreadsheet, a handwritten note, several PDFs), each with a hand-written answer key in samples/expected/. npm run eval runs them all and scores how many fields match and how many expected flags were raised.

The samples are built to contain traps. The Corvane PO limits DFARS to line 40 only. On its first run, the app put DFARS on all five lines. The answer key caught it, and the fix went into both the prompt and the normalizer. That's the loop: write a hard case, see it fail, fix the rule, keep the case as a test.

Words you'll hear

Glossary

RFQ
Request for quote. "What would this cost and when can you ship it?"
PO
Purchase order. A buyer's formal order, usually with terms, quality clauses and a need-by date.
Alloy
The metal's recipe, like 6061 or 7075 aluminum, or 718 nickel alloy (Inconel).
Temper
How the metal was heat-treated and stress-relieved, like T651 or T7351. Same alloy, different temper, different strength. Nox stocks specific tempers per alloy and form.
Plate / bar
The form of the stock. Plate is flat (thickness, width, length). Bar can be round (diameter, length), square or rectangular.
Spec callout
A standard the material must meet, like AMS 4078 or AMS-QQ-A-250/12. Many imply an alloy and temper on their own.
DFARS
U.S. defense rules. Clause 252.225-7009 covers "specialty metals" like nickel alloys and titanium, which must be melted in approved countries. Buyers often apply it to aluminum orders too.
Mill cert / MTR
The test report from the mill that made the metal, proving its chemistry and strength. Aerospace buyers require one with every shipment.
Cut tolerance
How far off the saw cut may be, like +.125/-0 (up to an eighth of an inch over, never under).
LLM
Large language model: the AI (Claude or GPT) that reads the document.
Schema / structured output
The exact form the AI must fill in, and the feature that forces it to reply in that form.
Payload
The body of the request sent to Nox's API.
Dry run
Showing exactly what would be sent, without sending it.
Idempotency key
A fingerprint on a request so that sending it twice doesn't create two RFQs.
Hash
A short fingerprint computed from a file's contents. Same file, same hash. Any change, completely different hash.
